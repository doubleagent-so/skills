# Resolve an ERC-8004 agent identity

Use this when a user wants to associate a conventional agent name with an Ethereum
registry token or inspect its sourced reputation. No wallet, gas or chain writes
are needed. Registry membership does not authenticate the browser making a visit.

## Read an identity

Set `DOUBLEAGENT_ETHEREUM_RPC_URL` to an HTTPS RPC for the requested chain. Keep
provider credentials in the environment. Run the bundled helper from the installed
skill directory (Node.js 18+; dependencies are bundled):

```sh
export DOUBLEAGENT_ETHEREUM_RPC_URL=https://ethereum-rpc.publicnode.com
node scripts/agents.mjs resolve --agent-name erc8004.agent-1 --token-id 1 --output identity.json --json
```

Token 1 is a public lookup example. `erc8004.agent-1` is a chosen local alias, not
the token's registered display name or a claim that its owner controls this run.
Replace both values for your agent. The equivalent CLI command is:

```sh
npx @doubleagent-so/cli agents resolve --agent-name erc8004.agent-1 --token-id 1 --json
```

The default chain is Ethereum mainnet (`1`), using the official identity registry
`0x8004a169fb4a3325136eb29fa0ceb6d2e539a432`. Use `--chain-id` and `--registry`
for another deployment; configure a matching RPC. Token and chain IDs are decimal
strings, including IDs larger than JavaScript's safe integer range.

Names use `operator.agent-name`, such as `acme.shopping-assistant`. Unknown names
are accepted; they need not exist in Double Agent's detector catalog. The separate
`agent_ref` combines namespace, chain, registry and token:

```text
eip155:1:0x8004a169fb4a3325136eb29fa0ceb6d2e539a432:1
```

The snapshot records owner, agent wallet, registration URI, finalized block number
and hash, and lookup time. Registration documents are often off-chain: this reader
retains their on-chain URI and does not fetch their contents. A missing URI remains
empty. `visit_binding` remains `unverified`.

## Read selected reputation

Choose reviewers you trust before requesting reputation. Replace the marked
address with a real reviewer; use comma-separated addresses for up to five:

```sh
node scripts/agents.mjs resolve --agent-name acme.shopping-assistant --token-id 22 --reviewers REVIEWER_ADDRESS --tag1 successRate --json
```

`--tag1` and `--tag2` filter metrics. Choose tags appropriate to that agent; do not
interpret unrelated metrics as a universal score. On custom deployments also set
`--reputation-registry`. The official Ethereum reputation registry is the default
only when using the official Ethereum identity registry.

Results retain the summary count, signed value, decimal scale, reviewer policy,
and up to five latest feedback records per reviewer, including revoked records.
For example, value `9977` with scale `2` means `99.77` in that metric's units.
Tag filters apply to the bounded feedback window; `feedback_truncated` indicates
older records were omitted. This is not a complete review history. Review prose,
off-chain documents and feedback event URI references are not fetched. No reviewers
means reputation was not requested; an unavailable result is not a zero rating.

## Declare identity on a website visit

With [simulation prerequisites](simulate.md) installed, run from the skill directory:

```sh
node scripts/simulate.mjs https://glood.ai --scenario agent --agent-name erc8004.agent-1 --token-id 1 --output simulation.json
```

This needs no RPC. It appends the following declaration to Chromium's actual UA:

```text
erc8004.agent-1/1.0 (erc8004=eip155:1:0x8004a169fb4a3325136eb29fa0ceb6d2e539a432:1)
```

A name alone (`--agent-name acme.shopping-assistant`) also works. Names are a
Double Agent convention; the optional ERC-8004 comment is our extension to normal
HTTP product/version syntax, not an ERC standard. The local report includes
`declared_identity` and snapshots include `declaredIdentity`. This does not change
the behavioral verdict. Token 1 remains an example, not an identity you control.

Add `--report` to send the installed SDK's telemetry and associate the declaration
with visits in the site's dashboard. This requires an API deployment supporting
these fields. It writes synthetic data to the SDK's configured account and does
not automatically mark it as test data. Without `--report`, standard Double Agent
telemetry stays blocked; the target still receives browsing requests.

To **also resolve** the blockchain identity into the local report, set the RPC
environment variable and add `--resolve-identity`. The `registry_identity` snapshot
stays local and `visit_binding: unverified`. Reputation flags require this option.

## Sign telemetry with an Ethereum wallet

Use Node 20+ and an API with migrations, Elasticsearch mappings and chain RPCs
configured. Have your secret manager set `DOUBLEAGENT_ETHEREUM_PRIVATE_KEY` in the
local process environment. Never put the private key in a command, page, report or
chat. Replace the example identity with your own registry token for a linked badge:

```sh
node scripts/simulate.mjs https://glood.ai --scenario agent --agent-name acme.shopping-assistant --token-id 22 --report --sign-requests --sign-api https://api.doubleagent.so --output signed-visit.json
```

Equivalent internal command from the repository root:

```sh
npm run simulate:site -- --url https://glood.ai --scenario agent --agent-name acme.shopping-assistant --token-id 22 --report --sign-requests --sign-api https://api.doubleagent.so --output /tmp/glood-signed.json
```

The public CLI accepts the same flags with its `simulate` subcommand.
`--sign-chain-id` defaults to the declared registry chain, otherwise `1`. Without a
registry claim, a valid signature can still receive the wallet badge.

Signing happens in Node, only for POST `/v1/collect` and `/v1/check` on the exact
`--sign-api` HTTPS origin and selected website host. Other traffic is not signed.
The server verifies the draft ERC-8128 SDK 0.4.1 profile, exact request and expiry,
and consumes each nonce once. Deployed ERC-1271 wallets can be verified by the API;
the bundled simulator signer uses an EOA private key. No chain transaction or gas.

The session dossier shows **Ethereum signed** for a verified request and
**ERC-8004 linked** only when the signer matches the claimed registry's owner or
agent wallet at the recorded block. Wrong keys, copied names and registry lookup
alone do not earn a linked badge. The badge does not establish AI behavior, good
conduct or authorization. The report's `signing.signed` count means signatures
were attached, not that the API verified them; inspect the dossier or check response.
Unavailable RPCs give no verification badge and do not stop detection. Delegated
and counterfactual wallets are not supported in this version.

## Save a site association

After signing in with the CLI, owners/admins can save or refresh a mapping on an
API deployment with registry support enabled. Replace the site, name and token:

```sh
npx @doubleagent-so/cli agents resolve --site st_YOURSITE --agent-name acme.shopping-assistant --token-id 22 --json
npx @doubleagent-so/cli agents list --site st_YOURSITE --json
npx @doubleagent-so/cli agents remove ari_ASSOCIATIONID --site st_YOURSITE --json
```

The bundled helper accepts these same arguments and uses the CLI's saved login or
`DOUBLEAGENT_SESSION`. Site operations use the API's configured RPC, not the local
RPC variable. Viewers can list mappings. Removal deletes only the site association,
never the blockchain identity. Re-resolving refreshes its snapshot; refresh is not
automatic. String fields have no foreign keys, catalog membership constraints or
SQL enum checks. One name may map to several registry references.

Saved mappings and read-only lookups are not proof of visit ownership. Direct signed
telemetry uses the verification described above; arbitrary forwarded hit records
and unsigned visits remain declarations.
